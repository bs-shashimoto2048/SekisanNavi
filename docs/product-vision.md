## 1. Sekisan Naviは何を目指していないか

最初に明確にしておく。

**Sekisan Naviは、現時点で積算を完全自動化することを目的とした完成形システムではない。**

短期的には、従来

```text
紙図面 → 人が目視 → 人が判断 → 積算
```

として行っていた作業の相当部分が、

```text
Sekisan Navi → 人が画面で確認 → 人が判断・修正 → 積算
```

へ変わるだけになる可能性がある。それ自体を失敗とは考えない。

### 1.1. 「紙からPCへ」の置き換えだけでは不十分

重要なのは、単に紙でのチェックをPC上でのチェックへ置き換えることそのものではない。それだけなら自動化への価値は限定的である。

Sekisan Naviで重要なのは、**そのPC上で行われた判断・修正・確定結果を、構造化されたデータとして残せること**である。紙の上で消えていた「なぜその積算コードを選んだか」「なぜ所属盤を変更したか」といった判断過程を、後から参照・分析可能な形で残せるかどうかが、単なるデジタル化と将来の自動化を分ける境界線になる。

### 1.2. 現在地点はゴールではなく始まり

> Sekisan Naviの現在地点はゴールではなく、将来の積算自動化に向けた始まりである。

現時点のUI・機能は、あくまでこの先の段階的な自動化のための土台と位置付ける。

---

## 2. 現在の3つの情報源と、それらを「変換して終わらせない」こと

現在Sekisan Naviが扱う積算情報は、大きく次の3つに整理できる。

- **AIによる拾い出し** (Detection、図面上のBBox検出)
- **社内データの流用** (`product_df` / `estcode_df` 等、設計データからの参照)
- **不足分に対するManual操作** (人が図面上へ手動でBBoxを追加・修正)

重要なのは、これら3つを最終積算コード(積算コード・数量・金額)へ変換して終わらせないことである。最終結果だけを残し、そこへ至る過程を捨ててしまうと、次に同じような判断が必要になったときに何も再利用できない。

### 2.1. 残す価値があるのは「結果」だけではない

将来自動化を行う際に価値があるのは、最終積算コード・数量・金額といった**結果**だけではない。可能な範囲で、

```text
入力 → 初期判断 → 人の修正 → 最終判断
```

という一連の関係を追跡可能にすることに価値がある。

### 2.2. 将来的に価値のある情報 (概念整理)

以下は「今すぐ全項目をDBへ保存せよ」という要求ではない。**将来、保存設計を検討するときに価値を評価すべき情報**として概念的に列挙する。

- AIが何を検出したか、AIの検出位置
- 社内データから何を取得したか
- Manualで何を追加したか
- BBoxをどのように修正したか
- どの盤へ所属すると判断されたか、所属を人が変更したか
- どの積算コードが最初に割り当てられたか、積算コードを人が変更したか (変更前 / 変更後)
- 要確認になった理由、人がどのように要確認を解決したか
- 最終積算コード・数量・金額
- 根拠図面、BBox、盤情報

## 3. 最重要原則: 通常業務の中で自然にデータが蓄積されること

> 作業者にデータ収集のための余計な入力を要求せず、通常の積算作業を行うだけで、
> 将来の自動化に利用可能な判断データが自然に蓄積されることを目指す。

これは非常に重要な原則である。将来AIに使えるからという理由だけで、

- 入力欄を増やす
- 変更理由を毎回入力させる
- 手順を増やす

といったことを安易に行わない。

### 3.1. 人の操作そのものをデータ化する

理想としては、

```text
通常業務 = 同時に将来の改善データ収集
```

となる構造を目指す。作業者が「自分は今AIの学習データを作っている」と意識する必要がない状態が望ましい。BBoxを移動する、積算コードを選び直す、所属盤を修正する——それらの**通常の操作自体**が、後から見返せる判断の記録になっている状態を目指す。

## 4. 段階的自動化 (目指す方向性であり、確定スケジュールではない)

以下はロードマップではなく、**目指す方向性**として記載する。

| Stage | 内容 |
|---|---|
| Stage 1 | 紙・目視中心の作業をSekisan Navi上へ移す |
| Stage 2 | AI / 社内データ / Manual / 最終確定結果の関係を蓄積する |
| Stage 3 | 人が繰り返している判断・修正を分析する |
| Stage 4 | 決定論的に解決できるものをルールやプログラムへ移す |
| Stage 5 | 積算コードや判断候補を自動提示する |
| Stage 6 | 十分に信頼できるものだけ自動確定する |
| Stage 7 | 例外・新規パターン・低信頼項目のみ人が判断する |

### 4.1. 最初から完全自動化を狙わない

完全自動化率を早期のKPIにはしない。現実的には、

```text
人が100件判断
  → システムが候補を絞る
  → 人が20件判断
  → 高信頼なものは自動確定
  → 人は例外だけを見る
```

という段階的な進化を想定する。

### 4.2. 「候補提示」も重要な自動化

例えば過去データから「この条件では過去の95%が18311」と判定できるなら、まず

```text
積算コード候補
1. 18311
2. 18302
3. ...
```

を提示するだけでも十分な業務改善になり得る。いきなり自動確定する必要はない。

---

## 5. AI利用率を目的にしない

これも非常に重要な原則である。将来、同じ条件で人が毎回同じ修正をしていることが分かった場合、それを**AIで学習すべきとは限らない**。解決手段としては、

- deterministic rule (決定論的なルール)
- 通常のプログラム
- Master (積算コードMaster等の参照データ)
- 社内データ連携
- AI

を比較検討する。

> 目標は、AI利用率を高めることではなく、人が判断しなければならない量を安全に減らすこと。

### 5.1. AIとルールの役割 (考え方の例示)

- 完全に決まるもの → Rule / Program
- 既存の社内データで決まるもの → Data integration
- 曖昧だが過去傾向があるもの → AI / Candidate recommendation
- 新規・低信頼・例外 → Human

## 6. 将来概念 (現時点で実装しない)

将来的な発展の方向性として、次のような概念を記載する。**現時点でこれを実装する計画ではない。**

```text
AI Detection
      +
社内設計データ
      +
product_df / estcode_df 等
      +
盤情報
      +
寸法
      +
接続情報
      +
周辺Detection
      +
過去の確定結果
      ↓
積算候補生成
      ↓
信頼度 + 根拠
      ↓
自動確定 / 候補提示 / 要確認
```

### 6.1. Sekisan Navi自身が改善基盤になる

将来的にはSekisan Naviを、**積算自動化機能そのもの**だけでなく、**何を自動化できるのかを調査・評価するための基盤**としても位置付ける。蓄積結果から、

- AI化すべき処理
- Rule化すべき処理
- 社内データ連携で解決できる処理
- 人に残すべき判断

を判断できることに価値がある。

## 7. 現在実装との関係

現在実装済みの以下の機能群は、**最終結果だけではなく判断過程を扱うための基盤**として位置付ける。

- AI / 設計情報 / Manualの情報源区別
- Detection / BBox
- 盤所属判定 (BBox交差判定)、製品全体、要確認
- 積算集約 (数量・金額を確認する場所) / 積算明細 (個々の根拠を1件ずつ追う場所)
- 図面へのトレーサビリティ、BBoxへのトレーサビリティ
- 編集追従 (所属変更時の画面追従)
- Undo / Redo

これらは現時点でも「なぜその積算コードになったか」を人が確認できる状態を提供しており、将来の判断データ蓄積へ自然に接続できる設計を意識している。

### 7.1. Undo/Redo履歴と将来データを混同しない

**注意**: 現在のUndo/Redoは、UI操作の取り消し・やり直しのための編集履歴として実装されている。これは将来的な分析用のaudit/history(誰が・いつ・なぜ判断を変更したか、を恒久的に残す記録)と必ずしも同一ではない。将来、判断過程を分析用に永続化する必要が生じた段階で、別途保存設計を検討する。

### 7.2. 現時点で保存していない情報を「保存済み」と書かない

本文書はあくまで理想・方向性を記載する文書である。現在DB等に永続化されていない履歴を「Sekisan Naviは保存している」と書いてはならない。常に、

- **現在実装済み**であること
- **将来保持する価値がある**(現在は保存していない)こと
- **今後検討**(方向性のみ、具体設計なし)であること

を区別して記述する。本文書内の記載も、この区別に従っている(第2章・第6章の情報一覧・将来概念は「将来検討」区分、第7章の現在実装との関係は「現在実装済み」区分)。

## 8. Design Principles

今後の設計判断で立ち返るための原則。

1. 最終結果だけでなく根拠を追跡できるか
2. 人による修正結果を必要以上に捨てていないか
3. AI / 社内データ / Manual等の情報源を区別できるか
4. 自動判断と人の判断を区別できるか
5. 通常作業の中で自然にデータが蓄積されるか
6. データ収集だけのために作業者へ負荷を増やしていないか
7. AIではなくRule/Programで解決すべき問題ではないか
8. 過去の確定結果と比較・分析できる構造になっているか
9. 自動化した判断にも根拠を残せるか
10. 例外を無理に自動化せず人へ戻せるか

---

## 9. まとめ

> Sekisan Naviは、積算自動化の完成形を最初から作ることを目的としない。現在の積算業務を
> デジタル化し、その過程で生じる判断・修正・確定結果を再利用可能なデータとして蓄積する
> ことで、将来の積算自動化へ段階的に進むための基盤を目指す。

> 現在地点はゴールではなく、自動化に向けた始まりである。
